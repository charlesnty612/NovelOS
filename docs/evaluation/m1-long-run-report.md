# M1 一致性衰减观测报告

- 运行窗口：2026-08-24 ~ 2026-08-25（含夜间休眠中断，纯运行时长约 6.4 小时）
- 配置：MiniMax-M3（openai_compatible，base_url api.minimaxi.com/v1，timeout_s=1800）
- 数据明细：`docs/evaluation/m1-data.md`（由 `scripts/m1_report.py` 生成）；原始现场 `data/m1_run/`
- 结论口径：所有分数均来自 `quality_reports` 实测落库，非估算。

## 1. 运行结果总览

| 指标 | 数值 |
| --- | --- |
| 完成章数 | **50 / 50** |
| Token 总耗 | **635 万**（prompt 297 万 / completion 338 万） |
| 单章均值 | 12.7 万 token；462 秒（约 7.7 分钟） |
| 质量门禁模式 | report（未阻断任何提交） |

百万字（≈500 章）线性外推：**约 6350 万 token、80+ 小时纯运行时间**。成本大头是 completion（53%），其中 commit 环节的 observer 输出最重。

## 2. 核心问题的答案：长程一致性没有衰减，衰减的是别的东西

**✅ 状态机经住了考验（本次最重要的正向结论）**

- continuity 子分全程稳定在 **99.4~99.7**（50 章无一跌落）；
- guardrails 零 fatal：角色死亡复用、世界规则矛盾、时间线回退、知识泄漏全部未触发；
- story_state 快照从 5KB 线性增长到 110KB，无爆炸、无损坏；
- What-if 分支与主线的隔离未被污染。

结论：**"设定崩坏"这一百万字头号杀手，在 50 章尺度上被 Canonical Story State 机制有效压制。**地基验证通过。

**❌ 真正的衰减发生在文风层（本次最重要的负向发现）**

- style 子分从 85.5（1-10 章）滑落到 75~76 并固化；
- 第 35~47 章出现**碎片化文风退化**：正文退化为"四十四过。四十三过。"式的 ≤10 字短句机械罗列（ch040/ch048 为实锤样本），ai_trace 同期降至 93；
- 该退化具有**连锁破坏性**：碎片化正文诱发 observer 对微状态变化穷举，输出爆炸导致 3×1800s 超时（ch040/ch048 各阻塞约 90 分钟）；
- **修复实证有效**：writer prompt 增补反碎片化硬规则（§6 Rules 13-16）后重写 ch040/ch048，commit 一次通过——证明文风退化可在 prompt 层拦截。

## 3. 其他观测

1. **节奏系统形同虚设**：pacing 全程钉死在 65，foreshadowing 恒为 0；H-3 规则（连续 3+ 章 payoff=0，error 级）自第 4 章起反复把 overall 打到 0。根因是 director 计划不产出可兑现的 payoff 事件、observer 也提取不到 resolved_hooks——爽点闭环在生成侧就没建立起来，而不是评审侧误判。
2. **字数系统性偏低**：单章均值 765~924 字，远低于番茄 1500-2200 最佳区间。部分根因是计划里 `target_word_count=700`。
3. **快照线性膨胀**：每 10 章 +~25KB，500 章将达 ~1.3MB，装配预算需要裁剪策略（摘要链已有，但快照本体进 observer 输入是全量的）。
4. **运维面**：双服务进程并存会导致 SQLite 锁挂死节点（已用 py-spy 定位，进程管理需单实例约束）；provider 存在小时级慢周期（成批 1800s 超时），断点续跑 + 按状态恢复的重试设计经受住了全部异常。
5. **干预记录**（均为 prompt 层，零业务代码侵入）：observer 增加"update 前必须核对 snapshot"规则（修 delta 口径拒绝）；writer 增加反碎片化/字数纪律/对话占比规则（修文风退化）。两次干预均实证有效。

## 4. 对 M2~M4 的直接输入

| 发现 | 指向 |
| --- | --- |
| 文风退化靠人工发现、prompt 救火 | M2 必须建 LLM judge 文风评审 + style 连续监测告警 |
| payoff 闭环从未建立、pacing 恒 65 | M2 的爽点密度量化要落在 director 计划侧（生成前约束），而非仅事后检测 |
| 字数偏低、target_word_count=700 | M2 校准 director 的字数目标到番茄标准（1500-2200） |
| completion 占 53%、observer 最重 | M3 成本看板按节点计量；observer 输出瘦身（max_changes 上限已留配置口） |
| 快照线性膨胀 | M3 引入快照分代/裁剪装配策略 |
| 双进程锁死、慢周期重试 | M3 异步队列需带单实例锁与健康探测 |

## 5. 结论

M1 回答了立项时的核心疑问："写完且不崩"的机制在真实模型下成立；"好看"的上限缺口被精确定位为三件事——文风稳定性、爽点闭环、字数纪律。这三件事全部指向 M2 的建设范围。
