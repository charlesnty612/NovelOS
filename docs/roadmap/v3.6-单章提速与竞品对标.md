## 二、关键数据真相：completion tokens ≈95% 是思考 token

ch064~ch067 审计（ai_call_logs vs output_json 字节数）：

| agent | completion tokens | 最终 JSON/正文 | 结论 |
|---|---|---|---|
| writer (ch066) | 49,296 | 2,856 B（≈1,900 汉字） | ~94% 为 MiniMax-M2 内部思考串 |
| director plan (ch066) | 21,654 | 3,828 B | 同上 |
| observer leg (ch066) | 13,640 / 17,332 | 2,791 / 3,980 B | 同上 |

**决策（P3 输出量控制暂不启用 max_tokens 硬顶）**：硬顶若低于"思考+JSON 总需求"会截断 JSON → 解析失败 → 重试同顶 → 必败循环。MiniMax 思考长度不可控且未公开下限。列为可调参数记录在案，待 V3.8 用更安全手段（见 §四）。

## 三、实测耗时对比

| 版本 | 章节 | 全链耗时 | 分解（plan/write/review/commit） |
|---|---|---|---|
| 修复前常态 | ~ch050s | >1200s（含无限挂起，最高观测 30min+） | — |
| V3.6 流式 | ch065 | 671s | 468.6→首挂起截停后 79.6/…（见 data/m1_run/ch065_stream.log） |
| V3.6+usage | ch066 | 658s | 205.8 / 187.6 / 0.1 / 264.6 |
| V3.6.0 全量 | ch067 | 866s | 223.7 / 354.8 / 0.2 / 287.4 |

ch067 偏高主因 = write 354.8s（completion 42,391 tokens，MiniMax 服务端解码波动），非本地环节。
review 阶段 0.1~0.2s 是因 `NOVELOS_CRITIC_MODE` 当前为 off/skip 配置（critic 可选采样开关，V3 已有）。
质量抽查：prose_chars=2397（目标带内）、quality_overall=77（ch066=89；critic off 时分数来自静态校验器，波动属内容差异；后续章节需跟踪）。

剩余瓶颈（定量）：plan+write 两段 550~580s ≈ 全链 65%，全部是 MiniMax 对大输入+超大思考输出的服务端解码时间。本地装配/DB/工作流开销每章 <15s。

## 四、竞品对标结论（调研子代理取证，GitHub 源码级证据）

### oh-story-claudecode（worldwonderer，5200+ star）
- 每章 13 步流程但**主线程只调 1 次写作 LLM** + 可选 consistency-checker；其余全是文件读写与确定性脚本。
- 一致性：单一权威状态 `追踪/_tracking-state.json` + state_revision 乐观锁 + 每章一次事务提交，派生视图（上下文卡 ≤12KB、角色卡 ≤8KB）。
- 输出控制：**字数带硬约束脚本** `wordcount_core.py`（visible_chars_v1 去空白计数，±12%/±15% 双带，under 不补 over 净删一次）。
- 明确禁止多章并发写。

### determinFlow + bishu-novel（alikon-art，AGPL-3.0）
- DAG 工作流引擎；bishu-novel 每章循环 mvp → polish(可选) → post-hoc，共 **8~14 次小调用**而非少数大调用。
- mvp 内部：骨架写手出 `[SLOT_*]` 叙事骨架 JSON → **5 个专项写手并行填槽**（对话/动作/内心/描写/过渡）→ 整合写手拼装扩写；节点级上下文隔离（写手只读裁剪后局部上下文），README 实称省 70%-89% token。
- post-hoc：观察员（不裁决）→ 仲裁者（temperature 0.3，adopt/pending/conflict）→ 回写 meta。
- prompt section 级 cache_break/token_estimate 设计，与我们 V3.6 键序重排同一思想。
- ⚠️ AGPL-3.0：只借鉴思想不复制代码。

### 架构判断（主控定调）

我们与竞品的根本差异：**竞品把"单章任务"拆成多个小输出（可并行、可控），我们把整章压在 1 个大输出里（writer 42k completion tokens），导致 wall time 被 MiniMax 思考 token 解码绑架。**

V3.8 方向建议（按性价比）：
1. **字数带硬约束移植**（oh-story wordcount_core 思想，纯 Python 自实现避 license）+ writer prompt 写明"正文目标 N 字"，把思考预算自然压缩；
2. **writer 分段写作**：按 scene/key_beats 把一章拆 2~3 段顺序生成（或并行），单次输出量降至 1/2~1/3；
3. 观察员+仲裁分离已在 observer 双腿具备雏形，暂无需引入 post-hoc 式裁决层；
4. 引擎级 DAG 运行时不迁移（单体已够用）。
