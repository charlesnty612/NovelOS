## 一、「skill」在赛道里的两种形态

### 1.1 形态 A：纯说明书包（prompt-only）

交付物是 `SKILL.md`（+ `references/`）本身，**没有可执行引擎**。Agent 读说明书、按说明书
调用外部工具。质量保证手段以**静态检查**为主：文件放对了没、frontmatter 合规没、脚本能不能跑过。

代表项目（2026-10-19 实测）：

| 项目 | 形态要点 | 自带「产物质量评测」？ |
|---|---|---|
| `Nanako0129/sepia` | 6 个 SKILL.md（1 个 router + 5 个操作 wrapper），**无运行时引擎**；另有 `scripts/check_versions.py` 强制版本一致性（**守卫**不是引擎） | **有**：`claude plugin eval` 行为评测（1 case / 3 grader，`--threshold 0.7`） |
| `danjdewhurst/story-skills` | 24 个 SKILL.md，**只带 `name` + `description` 两个 frontmatter 键**（最纯粹的说明书包） | **有但不进 CI**：真模型 fixture 评测（37 fixture）**手工跑**；CI 只跑确定性一半 |
| `zenstory-ai/oh-story-claudecode` | 13 个 SKILL.md + `references/` 知识库；`scripts/` 下是**围绕说明书的守卫与工具**（23 个 `check-*` + 44 个 `test-*`），不是被 agent 调用的业务引擎 | ⚠️ `scripts/bench/` 预注册非劣效基准，**刻意不进 CI** |

⚠️ 形态 A 与形态 B 之间**没有干净的界线**（见 §1.2 末段的边界情形说明）。

### 1.2 形态 B：带引擎的 skill

除说明书外还带**可执行引擎**（CLI / 守护进程 / 服务），agent 通过**命令行或 HTTP** 驱动它。
质量保证多出「引擎自己的测试 + CI」这一层，但**引擎测试与产物质量是两件事**（§五·反例）。

| 项目 | 引擎形态 | 自带「产物质量评测」？ |
|---|---|---|
| `Narcooo/inkos` | `@actalk/inkos` CLI（快照 33 个命令文件 → 上游 27 个）+ `core`（纯逻辑库）+ `studio`（Web）；**统一 action kernel** | ⚠️ 产品内**有** prose 评审能力（AI 痕迹检测、外部 AIGC 检测器），但**CI 不评任何产物质量** |
| `xiaohai-uid/storyrepo` | `engine/storyrepo/`（**纯标准库 CLI**，17 个测试文件 / 214 个测试函数） | **无**（机检门禁是确定性规则，不是产物质量评测） |
| `danjdewhurst/story-skills`（**边界情形**） | 有确定性维护 CLI（`bin/`、`src/`、`scripts/`，如 `skills/story-maintenance/scripts/story.js`）与 npm 分发，但**没有常驻服务** | ⚠️ 真模型 fixture 评测**手工跑**，CI 只跑确定性一半 |
| `zenstory-ai/oh-story-claudecode`（**边界情形**） | 25 个静态守卫入口 + `skills/story/scripts/dashboard-server.mjs`（本地 Dashboard）——**是工具链不是业务引擎** | ⚠️ `scripts/bench/` 有预注册非劣效门槛，**刻意不进 CI** |

⚠️ **A/B 不是二分**：中间形态（**说明书 + 工具链，无业务引擎**）在生态里最常见。
真正的分野不是「有没有代码」，而是「**agent 是通过命令面驱动一个真实系统，还是只读说明书**」——
`story-skills` / `oh-story` 属前者与后者之间：它们的代码是**围绕说明书的守卫与维护工具**，
不是被 agent 调用的业务引擎。**把它们算进「带引擎」会夸大「引擎层」的普遍性**，
故上表对这两个边界情形单独标注。

## 二、Agent Skills 规范 vs Claude Code 扩展的 frontmatter

### 2.1 规范侧：6 个字段，未知键是**硬错误**

规范原文（`https://agentskills.io/specification`，Frontmatter 表）：

| Field | Required | Constraints |
|---|---|---|
| `name` | Yes | Max 64 characters. Lowercase letters, numbers, and hyphens only. Must not start or end with a hyphen. |
| `description` | Yes | Max 1024 characters. Non-empty. Describes what the skill does and when to use it. |
| `license` | No | License name or reference to a bundled license file. |
| `compatibility` | No | Max 500 characters. Indicates environment requirements… |
| `metadata` | No | Arbitrary key-value mapping for additional metadata (a map from string keys to string values). |
| `allowed-tools` | No | Space-separated string of pre-approved tools the skill may use. (Experimental) |

**「未知键是硬错误」是可执行的，不是口号**——规范配套的参考实现 `skills-ref` 里：

```python
# agentskills/agentskills:skills-ref/src/skills_ref/validator.py
ALLOWED_FIELDS = {
    "name",
    "description",
    "license",
    "allowed-tools",
    "metadata",
    "compatibility",
}

def _validate_metadata_fields(metadata: dict) -> list[str]:
    """Validate that only allowed fields are present."""
    errors = []
    extra_fields = set(metadata.keys()) - ALLOWED_FIELDS
    if extra_fields:
        errors.append(
            f"Unexpected fields in frontmatter: {', '.join(sorted(extra_fields))}. "
            f"Only {sorted(ALLOWED_FIELDS)} are allowed."
        )
    return errors
```

命令行入口 `skills-ref validate ./my-skill` 在有错时 **exit 1**，逐条打到 stderr：

```python
# agentskills/agentskills:skills-ref/src/skills_ref/cli.py
    errors = validate(skill_path)
    if errors:
        for error in errors:
            click.echo(f"  - {error}", err=True)
        sys.exit(1)
```

⚠️ 细节：`_validate_metadata_fields` 拿的是**解析后的原始 frontmatter dict**
（`parser.py::parse_frontmatter` 用 `strictyaml` 解析后原样返回 `parsed.data`），
所以未知键**不会在解析阶段被悄悄丢掉**，而是留给 validator 报错。
（`SkillProperties` 那个 dataclass 是另一条消费路径，它只取声明过的键——
**两处行为不同，不能用 dataclass 的「安静忽略」去否证 validator 的「硬错误」**。）

### 2.2 Claude Code 侧：**20** 个字段，未知键**静默忽略**

`https://code.claude.com/docs/en/skills.md` 的 frontmatter 表共 **20 行**：
`name` / `description` / `when_to_use` / `argument-hint` / `arguments` /
`disable-model-invocation` / `user-invocable` / `allowed-tools` / `disallowed-tools` /
`model` / `effort` / `context` / `agent` / `background` / `hooks` / `paths` / `shell` /
`metadata` / `license` / `compatibility`
（其中 **14 个**是规范没有的 Claude Code 扩展。）

原文：

> All fields are optional. Only `description` is recommended so Claude knows when to use the skill. A field name must match the table exactly, hyphens included: **Claude Code ignores a field it doesn't recognize without reporting an error.**

⚠️ **连畸形 YAML 也不报错**（同一页）：

> If the YAML between the markers doesn't parse, the skill still loads with no fields set.

⇒ **两侧的失败模式是相反的**：规范侧「多写一个键 ⇒ 打包/上传硬失败」，
Claude Code 侧「多写一个键 ⇒ 静默忽略」（连 `name`/`description` 都不强制，
`name` 缺省取目录名、`description` 缺省取正文首个非空行）。

### 2.3 顶层 `version`：Claude Code 静默忽略 / claude.ai 上传硬失败

顶层 `version` **不在规范的 6 个字段里**，也**不在 Claude Code 的 20 个字段表里**
（该表连 "version" 这个词都不出现）。后果分两种：

| 路径 | 顶层 `version` 的下场 | 依据 |
|---|---|---|
| Claude Code 本地加载 | **静默忽略**（按 §2.2 的「不认识的字段不报错」规则） | `code.claude.com/docs/en/skills.md` |
| claude.ai skill 上传 / Skills API / `package_skill.py` 打包 | **硬失败**，错误原文：<br>`Unexpected key(s) in SKILL.md frontmatter: argument-hint. Allowed properties are: allowed-tools, compatibility, description, license, metadata, name` | 同页「Using skill frontmatter outside Claude Code」 |

该页把「两条分发路径可用字段」并排列成一张表：

> | Distribution path | Frontmatter fields you can use |
> | :- | :- |
> | Claude Code skills at any level, including plugin skills | Every field in the table above |
> | claude.ai skill uploads, the Skills API, and packaging with `package_skill.py` from anthropics/skills | `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools` |

⚠️ **规范自己的示例就把 `version` 放在 `metadata` 下**（`agentskills.io/specification`）：

```yaml
---
name: pdf-processing
description: Extract PDF text, fill forms, merge files. Use when handling PDFs.
license: Apache-2.0
metadata:
  author: example-org
  version: "1.0"
---
```

⇒ **合规写法是 `metadata.version`，不是顶层 `version`。**
（这不是「规范建议」，而是「规范示例 + 校验器实现」双重确认的形状。）

### 2.4 实测：同侪里踩这个坑的比例

| 项目 | 实测（2026-10-19） | 形状 |
|---|---|---|
| `zenstory-ai/oh-story-claudecode` | 13 个 SKILL.md 中 **11 个**带**顶层** `version:`（未带的两个是 `skills/browser-cdp/SKILL.md` 与 `skills/story/SKILL.md`——这两个也恰好是仅有的两个「只含合规键」的文件） | ❌ 违规写法：Claude Code 静默忽略；claude.ai 上传硬失败 |
| `Nanako0129/sepia` | 6 个 SKILL.md 中**仅** `skills/sepia/SKILL.md` 带版本，且写作 `metadata:` → `version: "0.12.4"` | ✅ 合规形态 |
| `Nanako0129/sepia` | 另有 `scripts/check_versions.py` **机器强制**该形状 | 见下 |
| `danjdewhurst/story-skills` | 24 个 SKILL.md **只带 `name` + `description`**，无任何 `version` | ✅ 不踩 |

⚠️ **oh-story 不用 `metadata.version`，但原因不是「知道规范」**：
它的 13 个 `metadata:` 全是**单行 JSON 对象**，唯一成员是 `openclaw`
（`metadata: {"openclaw":{"source":"https://github.com/zenstory-ai/oh-story-claudecode"}}`），
且**明文规定**必须保持单行：

> `AGENTS.md@main:11` —— **frontmatter 单行键值**：`description` 不用 `|`/`>` 块，`metadata` 是单行 JSON，OpenClaw 依赖这一点。
>
> `CONTRIBUTING.md@main:48` —— 为兼容 OpenClaw，frontmatter 必须保持单行键值：`description` 不使用 `|`/`>` 块，`metadata` 必须是单行 JSON 对象。

⇒ 它把 `version` 放顶层，是**为兼容某个宿主而牺牲规范合规**，不是规范无知。
**这正是「顶层 `version` 是违规写法」这个结论的实践价值**：违规不会立刻报错，
它一直跑到**上传那一刻**才炸。

sepia 的强制器值得抄（它把「版本一致性」变成一条 CI 闸门）：

```python
# Nanako0129/sepia:scripts/check_versions.py
REQUIRED = (
    ".claude-plugin/plugin.json",
    ".codex-plugin/plugin.json",
    ".qwenpaw-plugin/plugin.json",
    "skills/sepia/SKILL.md",
)
```

其 docstring（`scripts/check_versions.py:170-188`）把「版本只能写在 `metadata` 的直接子键下」
的判据写得很死：

> Only a `version:` that is a DIRECT child of a block-style top-level `metadata:` counts. Inline metadata (flow mappings, scalars) is refused with instructions to use block style… Declaring version more than once is an error, not a first-wins pick: duplicate-tolerant YAML parsers commonly keep the last value, so picking the first can pass on a stale one (issue #39).

⚠️ **附带发现（oh-story 自己的三套版本号互不一致）**：
`skills/story-long-write/SKILL.md` 顶层写 `version: 1.0.0`，
`.clawhub/publish.json` 里同一 skill 是 `1.1.42`，bundle 版本是 `0.9.0`。
⇒ **版本号散在三处、互不校验**，是「顶层 version 无机器语义」的另一个代价。

## 三、三平台 marketplace 的 `source` 形状互不兼容

**结论：必须分平台各写一份，不能一稿多投。** 三个平台对 `source` 的**类型要求**不同。

### 3.1 Claude Code —— 相对路径必须 `./` 开头

`https://code.claude.com/docs/en/plugins/marketplace-reference.md` 原文：

> | Type | Fields | Notes |
> | :- | :- | :- |
> | Relative path | the string itself | A directory inside the marketplace, resolved from the marketplace root. **Must start with `./`**, unless you write a bare name under `metadata.pluginRoot`. `"."` on its own means the root itself |

错误串（同一页 Validation messages 表）：

> | `plugins.i.source: Invalid string: must start with "./"` | Error | A relative-path `source` without the leading `./`. Before v2.1.285, this mistake printed `Invalid input` instead |

**例外（v2.1.239+）**：设了 `metadata.pluginRoot` 时可以写裸名——

> A bare name is a single directory name with no `/`, such as `"formatter"`. To write bare names instead of `./` paths, set `metadata.pluginRoot` to the directory they resolve under. With `"pluginRoot": "./plugins"`, `"source": "formatter"` resolves to `./plugins/formatter`.

⚠️ 但**「裸名」是 Claude Code 的特例，不是通例**——Cursor 那边裸名才是常态（§3.3）。

Claude Code 的 `source` 其实是个**并集**：相对路径字符串、或者带判别式的对象
（`github` / `url` / `git-subdir` / `npm` / `archive` / `command` 六种类型）。实测两种都在用：

```json
// Nanako0129/sepia:.claude-plugin/marketplace.json —— 字符串相对路径
{ "name": "sepia", "source": "./", ... }
```
```json
// danjdewhurst/story-skills:.claude-plugin/marketplace.json —— 带判别式的对象
{ "name": "story-skills",
  "source": { "source": "url", "url": "https://github.com/danjdewhurst/story-skills.git" },
  ... }
```

### 3.2 Codex —— `.agents/plugins/marketplace.json`，判别式对象

Codex 自己的源码给出了权威形状（`openai/codex:codex-rs/core-plugins/src/marketplace.rs`）：

```rust
pub enum MarketplacePluginSource {
    Local { path: AbsolutePathBuf },
    Git { url: String, path: Option<String>, ref_name: Option<String>, sha: Option<String> },
    Npm { package: String, version: Option<String>, registry: Option<String> },
}
```

落盘形态（`Nanako0129/sepia:.agents/plugins/marketplace.json` 原文）：

```json
{
```

### 3.3 Cursor —— `.cursor-plugin/marketplace.json`，`source` 是**裸目录名**

Cursor 的 schema 是一等公民（`cursor/plugins:schemas/marketplace.schema.json` 原文）：

```json

  "required": ["name", "source"],

      "minLength": 1,

    },
    "description": { "type": "string", ... },
    "minClientVersions": { "$ref": "#/$defs/minClientVersions", ... }
  }
}
```

Cursor 官方 marketplace（`cursor/plugins:.cursor-plugin/marketplace.json`）用的正是**裸目录名**：

```json

```

⚠️ 但**裸名不是 Cursor 的唯一写法**：schema 只约束「字符串」，`"./plugins/x"`（带 `./`）与

| `saadeghi/daisyui` | `"."` 与 `"packages/blueprint"` |

## 八、通用纪律

> **竞品快照的每个数字都是某个时点的值，写文档时必须标采集日期；超过一个版本周期未复核的数字一律视为过期。**

配套的取数纪律（本文档全程遵守）：

1. 引用外部仓库的结论**必须**是亲眼读到的文件内容，能给原文片段就给；不凭印象。
2. 「某仓有/无某能力」这类**否定性结论**，强度只配到**扫描覆盖面**——
   「扫过 N 处未见」≠「不存在」，须写明扫了哪些路径。
3. **工作流计数要剔除平台提供的 `dynamic/...`**；否则会把 GitHub 的动态工作流算成仓库资产。
4. **文件数 ≠ 用例数**；**测试文件数 ≠ 断言密度**；**测试文件 ≠ 测试套件**
   （oh-story 的 44 个测试文件在 `scripts/` 下，不在 `tests/` 下）。
5. **量具口径要对齐被测物**：`*.test.ts` 的 glob 与 `*.test.tsx` 的 glob 会差一个文件
   （`inkos` 的 cli 在其快照上是 42 而非 41——差的是 `tui-dashboard.test.tsx`）。
6. **「规范的推荐」与「某个仓库的做法」必须分开陈述**（§4.3 的两条错配即由此而来）。
7. **上游平台提供的方法不能记成某个仓库的自研方法**（§5.1a 的双臂 Δ 属 Claude Code 文档）。
