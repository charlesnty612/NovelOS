> 日期：2026-09-11。调研对象：`https://github.com/Narcooo/inkos`（当红开源 AI 小说创作项目）。
> 定位前提：**NovelOS 为纯自用工具**（2026-09-11 用户裁决）——本份结论按此前提裁剪优先级；
> 若日后转为公开发布，需重估「对外分发」类建议（见 §六·搁置区）。

> NovelOS 能力矩阵 / 实证交叉验证）+ 主会话逐条复核关键结论。
> InkOS 源码快照：`D:\zcodeproject\_refs\inkos`，HEAD `0910483`（v1.8.0）。
>
> **数据时效提示**：stars / issue 数会持续变化，本文数字均标注采集日期，引用时注意。

## 一、结论摘要

| # | 结论 | 状态 |
|---|------|------|
| 1 | InkOS 的核心竞争力是「多 Agent 流水线 + 结构化真相文件 + 审计修订闭环」，不是「AI 写小说」概念本身 | 已核实 |
| 2 | 它真正的传播杠杆是 `skills/SKILL.md` + 33 个 CLI 命令，使其可被外部 Coding Agent（Claude Code / Cursor / OpenClaw）调用，进入 ClawHub / SkillsLLM 技能市场 | 已核实 |
| 3 | **9.7k stars 与工程质量不匹配**：232 条 open issue，大量 2026-05 起的老 bug 未关，`pushed_at` 停在 2026-08-25 | 已核实 |
| 4 | 其用户痛点高度同源，集中在文件状态一致性、上下文膨胀、模型配置三处——**NovelOS 在架构上已规避前两类，第三类更优** | 已核实 |
| 5 | NovelOS 真实缺口仅两条：**全局 token 预算无硬顶**、**agent 调用面缺原子命令层**（后者按自用定位降级） | 已核实 |
| 6 | 架构无关、且自用也会踩的一条：**LLM 对「内容配比」类指令的持续遵守能力弱**（InkOS #260），NovelOS scene_planner 目前只硬约束字数、未见内容配比约束 | 待自查 |

## 四、五条假设的验证结论

> 调研前主会话提出 5 条假设，交由实证对比子代理逐条验证。**其中 2 条被推翻或修正**，
> 记录于此以免日后重蹈。

| # | 假设 | 判定 | 修正要点 |
|---|------|------|----------|
| H1 | 状态一致性架构是结构性分野（JSON 文件 vs SQLite） | **部分成立** | 主会话原表述「InkOS 无事务、无原子写」**错误**。实际有原子文件集 + 写锁 + staging + 快照。真实差异是**写路径覆盖度**（原子写仅用于特殊路径）与**可回溯性**（覆盖式快照 vs 不可变 commits 表） |
| H2 | InkOS 上下文全量投喂无裁剪 | **部分成立** | 原表述「完全无裁剪」**不准**。已有字符级 cap + 行级 filter + 治理上下文 v2（`rule-stack.yaml` / `trace.json`）。準确表述：**无 token 硬顶，关键路径（spot-fix / Settler）漏裁剪** |
| H3 | NovelOS 的模型配置架构更健全 | **成立** | 辅以反向学习点：InkOS 的「测试连接」两步探测体验、模型目录持久化、`releasedAt` 字段值得借鉴 |
| H4 | 对外 Agent 接口层是最大缺口 | **成立，但按自用定位降级** | 见 §六 |
| H5 | 创作引导有缺口 | **成立，但 NovelOS 已覆盖** | InkOS `book create` 单步走完、无分关卡审阅；NovelOS `project_init` 四关卡 + `step_mode` + `human_input.revisions` 三层 fallback 已结构覆盖 #285/#62/#49/#54 |

### 4.1 主会话被推翻的两处判断（留档）

1. **「InkOS 以 JSON/MD 为唯一真相源、无事务保证」** → 错。有 `commitAtomicFileSet`
   原子写、跨进程写锁、索引自愈（`rebuildChapterIndexFromFiles`）。正确的差异不是
   「有无事务」而是「原子性 ≠ 可回溯性」。
2. **「NovelOS 完全没有 token 预算机制」** → 不准。`_truncate_summaries_to_token_budget`
   （`packages/core/context_engine/builders_common.py:953-972`）确实在跑，但**只作用于
   director 的摘要链、预算固定 800 token**（`director_input.py:174-175`）。

## 五、NovelOS 对位优势（证据已复核）

| 维度 | InkOS | NovelOS |
|---|---|---|
| 状态存储 | JSON 状态 + MD 投影 + SQLite 记忆（三层）；部分路径裸写 | SQLite 37 业务表；迁移 0001~0023 |
| 提交语义 | 覆盖式快照回滚，无可回溯记录 | `commits` 不可变行 + `rollback_of` 部分唯一索引（`0022`）+ 单事务写 7 张领域表 |
| 并发控制 | 文件锁 + 心跳 + 租约 | 乐观锁（`previous_state_version`）+ DB 约束 + 分类型错误 |
| 崩溃恢复 | 索引自愈 + 快照 | `recover_interrupted_runs` 启动自愈 + `rebuild_snapshot_collections_from_db` |
| 上下文裁剪 | 字符级 cap + 行级 filter；无 token 硬顶 | relevance trim（默认开）+ paged 分层 + `inject_mode` 三态 + 摘要 cap + FTS5 召回 top-3 |
| 模型配置 | 端点硬编码白名单（44 个 endpoint 文件内嵌清单） | `model_profiles` + `capability_bindings` 纯数据驱动，任意 model id 字符串；`profile_ids` 数组顺序即 fallback 序 |
| 工作流韧性 | 顺序执行 + 取消传播 | checkpoint 断点续跑（512KB 软上限）+ PAUSE/RESUME + 协作式 CANCEL 双探针 |
| 质量门禁 | 33 维审计 + 审查阈值 85 | 8 guardrail + 七维评分 + enforce/report 双模式 + 字数带硬约束（target ±15%, floor 1200）|
| 对外调用 | SKILL.md + 33 CLI 命令 + HTTP 三入口 | 仅 HTTP（89 paths / 133 operations，24 个 router） |

## 六、补强建议（按「纯自用」定位裁剪）

### 6.1 建议做（1 条）

**全局 token 预算硬顶**——无条件成立，与自用/公开无关。

- 现状：`_TOKEN_BUDGET = 8000` 定义于 `packages/core/context_engine/preview.py:37`，
  全仓仅 3 处引用（定义 + `preview.py:525-526` 两个返回字段），**无任何代码读它做裁剪或失败**。
  `within_budget` 只是展示用 boolean。
- 风险同源：InkOS #80（五十章后单章 40 分钟）、#84（摘要越传越大 50 章后不可用）即此类。
  NovelOS 的裁剪是「按字段降级」，无全局兜底。
- 可行做法：把 `_truncate_summaries_to_token_budget`（`builders_common.py:953-972`）
  从「仅 director 摘要链」推广到全局装配，超预算时告警或降级。
- 工作量：小（机制已在，缺的是覆盖面与兜底策略）。

### 6.2 建议自查（1 条，架构无关）

**内容配比约束**——对应 InkOS #260。

NovelOS `scene_planner` 已强制每个 scene 填 `target_words`（字数分摊，见
`_inject_scene_word_budget`，`builders_common.py:986`），这是**形式约束**。
但「权谋 vs 感情」这类**内容配比**是否在 director / scene_planner 阶段有硬约束，未见明确机制。

InkOS 的经验是：靠 writer 自觉 + 事后审计无效（用户改 focus、重写、驳回都只维持两三章），
**必须在规划阶段就硬性约束场景分配**。建议自查 director-plan 的 schema 与 prompt，
确认内容配比是否可被显式声明并逐章核销。

### 6.3 搁置区（自用定位下降级，若转公开发布需重估）

| 项 | 原因 |
|---|---|
| CLI 原子命令层 + SKILL.md | 自用场景 agent 可读代码调用 HTTP，投入产出比不成立。**注**：`pyproject.toml` 实测无 `[project.scripts]`，无安装式 CLI 入口；InkOS 的传播力 = 33 CLI 命令 + SKILL.md 说明书 + 统一 action kernel，SKILL.md 只是说明书的附属，顺序不可倒置 |
| LICENSE 声明 | 项目实测**无 LICENSE 文件**、`pyproject.toml` 无 `license` 字段。私有自用无影响；公开发布则为硬阻塞（无声明=默认保留全部权利，他人无法合法使用） |
| Docker 部署 / 账户鉴权 | 本地优先是本项目定位（对应 InkOS #388/#369） |

### 6.4 明确不必跟风

| 项 | 依据 |
|---|---|
| 互动影游 / Open World / 剧本分镜 | 社区反馈显示用户实际主要用网文（`interactive-film` / `play` / `script-storyboard` 三套域模型，工作量「大」而自用收益低） |
| 33 维审计的规模 | 覆盖常见 5 类 + 失败可解释已足够，维度堆叠带来维护成本 |
| 复杂文风指纹系统 | 现有 `author_style_samples`（≤2 篇 × ≤1000 字）+ 拆书 canon 转风格卡已覆盖主要诉求 |
| 多语言 README / CHANGELOG | 自用无意义 |
| 模型平台站台式背书 | 无实际功能收益 |
